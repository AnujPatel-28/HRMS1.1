## Bugs found

### BUG-01 · Monthly leave accrual is running, and it inflates balances without allocating them

```
TITLE:      Leave accrual runs monthly and adds to `balance` without touching `total_allocated`
CASE:       fixture pre-flight (contradicts 00-README.md §1 and 01-accounts-and-fixture.md §3)
MODULE:     Leave
SEVERITY:   Major  (feeds payroll; also affects real tenants, not just QA)
ACCOUNT:    n/a — a scheduled job, observed as project_admin
WHEN:       fired 2026-09-01 00:00:00.034 UTC

STEPS:
1. Read leave_balances for the QA tenant, year 2026.
2. Compare against the seeded values in 01-accounts-and-fixture.md §3.

EXPECTED:   CL 12.0, EL 18.0. The docs state fn_accrue_monthly_leaves "exists but is not
            scheduled" and that "balances never grow on their own".
ACTUAL:     CL 13.0, EL 19.25, used_days still 0, last_accrual_date = 2026-09-01 for every
            monthly-accrual row. The increments are exactly days_per_year/12
            (12/12 = 1.0 and 15/12 = 1.25), so fn_accrue_monthly_leaves definitely ran.
            It is NOT an InsForge schedule — `schedules list` shows only
            attendance-derivation-hourly — so something else (pg_cron) is firing it.
```

Three distinct defects:

1. **The docs are wrong about it being unscheduled.** It fired on the 1st of the month.
2. **The function is wrong.** It does `balance = balance + days_per_year/12` and never updates
   `total_allocated`, so the ledger identity `balance = total_allocated + carried_forward -
   used_days` breaks the first time it runs. Worse, `total_allocated` was already seeded with a
   **full year** (12), so accrual is stacking a second year's entitlement on top: by 2026-12-01
   CL would read 12 + 12 = 24 days.
3. **Any authenticated employee can fire it**, and it has no tenant filter.
   `migrations/20260817130000_revoke-public-execute-on-secdef-functions.sql:70` does
   `GRANT EXECUTE ... TO authenticated`. Verified live: signed in as `employee-qa` and called
   `fn_accrue_monthly_leaves()` — **accepted, no permission error**. It is SECURITY DEFINER and
   loops over `leave_balances` for *every tenant in the database*.
   *Blast radius is limited* by the `last_accrual_date < date_trunc('month', CURRENT_DATE)` guard,
   which makes it idempotent within a calendar month — so this cannot be looped to inflate
   balances. But an ordinary employee of one tenant can trigger accrual for all tenants, and the
   guard is the only thing standing between this grant and unbounded self-service leave.

**Where it is scheduled from:** `pg_cron` **is installed**, and the only InsForge schedule is
`attendance-derivation-hourly`, so the job lives in `cron.job`. The project admin key cannot read
schema `cron` (403), and **no migration in `migrations/` registers it** — so it was created
out-of-band and is not in version control. Someone with database owner access needs to
`SELECT * FROM cron.job` to find and unschedule it.

**Not confined to QA.** A real tenant's SL type (48 days/yr, monthly) accrued the same night —
balances there now read 35–36.

### BUG-03 · A submitted task can still be rewritten by the employee

```
TITLE:      Employee can edit a task after submitting it for review
CASE:       TP-03
MODULE:     Task/Project
SEVERITY:   Major
ACCOUNT:    employee-qa@talentmeshsolutions.com
WHEN:       2026-09-02

STEPS:
1. As hr-qa, create a task assigned to QA Normal Employee.
2. As employee-qa, set its status to `submitted`.
3. As employee-qa, update the task's title.

EXPECTED:   Refused. TP-03: "the employee cannot then edit it out from under the reviewer".
ACTUAL:     The update succeeded — the title was rewritten while the task sat awaiting review.
```

RLS on `tasks` scopes the employee to their own rows but does not freeze them at `submitted`.
A reviewer can therefore approve a task whose text differs from what was submitted.

**The real submit path has the same hole** — checked, not assumed. The app submits via
`db.rpc("submit_task_request", …)`; that function inserts a `task_submissions` row and sets
`tasks.status = 'submitted'`, and **sets no lock column of any kind**. So reaching `submitted`
through the app leaves the row exactly as editable.

*Scope of the damage:* the submission's own `notes` / `attachment_url` are preserved immutably in
`task_submissions`, so those cannot be rewritten. What stays editable is the **task itself** —
`title`, `description`, `due_date`. Enough to change what the reviewer thinks they are approving.

*Filed the way `00-README.md` files this shape:* the data layer permits it. Whether the employee
UI actually offers an edit control on a submitted task is **untested** — that half needs a
browser. Even if the UI hides the control, the RLS hole is real and callable directly.

## BUG-06 · HR cannot create an employee at all — "Rate limit exceeded" on the very first attempt

```
TITLE:      Employee creation is hard-blocked; check_rate_limit has no EXECUTE grant and its
            permission error is reported to HR as a rate limit
CASE:       OM-12
MODULE:     Organisation
SEVERITY:   Blocker
ACCOUNT:    hr-qa@talentmeshsolutions.com
WHEN:       2026-09-02 12:06 IST
BROWSER:    Brave, Windows 11

STEPS:
1. /hr/employees/create → Step 1, fill Full Name "QA Temp Tester",
   email qa-temp-tester@talentmeshsolutions.com, phone 9876543210.
2. Click "Verify" (mandatory — "Next" stays disabled until verification completes).

EXPECTED:   The email verification step starts and the wizard can proceed.
ACTUAL:     Red inline error: "Rate limit exceeded. Please try again later."
            Console: "Function Error: Object". No employee row is created.
```

**Root cause, proven — it is not a rate limit.**

1. `rate_limits` holds **zero rows** for this tenant, so nothing had been counted.
2. `create-employee-user` builds its client from the **caller's** token
   (`createClient({ baseUrl, edgeFunctionToken: callerToken })`) and calls
   `check_rate_limit`, then does `if (rateLimitErr || rateLimitOk === false) → 429
   "Rate limit exceeded"` — collapsing a *permission* failure into a *rate-limit* message.
3. Calling `check_rate_limit` directly as `hr-qa` returns
   **`permission denied for function check_rate_limit`**.
4. Its ACL is `project_admin=X/project_admin` — **`authenticated` has no EXECUTE**.

**How it got this way:** `migrations/20260817100000_revoke-anon-execute-on-secdef-functions.sql:33`
and `migrations/20260817130000_revoke-public-execute-on-secdef-functions.sql:24` both revoke
EXECUTE from `authenticated`, and **neither re-grants it**. Compare
`fn_accrue_monthly_leaves`, which *is* re-granted on line 70 of the same migration. So the
2026-08-17 hardening pass has been blocking all employee creation ever since.

Note the same migration pair produces both this Blocker (under-granted) and BUG-01 part 3
(over-granted). The re-grant list wants an audit, not just this one line.

**Fix:** `GRANT EXECUTE ON FUNCTION public.check_rate_limit(uuid, uuid, text, integer, interval)
TO authenticated;` — and separately, stop reporting `rateLimitErr` as a rate limit; it should
surface as a 500 with the real message, or fail open.

**Knock-on:** OM-12, OM-13 (duplicate email) and OM-15 could not be executed — all of them need
an employee to be creatable. OM-13's specific worry is answered though: **no partial employee
record was created** by the failed attempts (`employees` has no `qa-temp-tester` row).

**Second blocker behind it:** even with the grant fixed, the wizard requires a 6-digit OTP
emailed to the new employee (`create-employee-user` → `verify-employee-code` →
`set-employee-password`, and `handleSubmit` refuses unless `authStep === "done"`). **SMTP is not
configured**, and the OTP is not stored anywhere in `public` that HR could read. So employee

```

            half_day_cutoff_override "--:--" (SQLSTATE 22007)
```

Response: `400 {"code":"22007","message":"invalid input syntax for type time: \"--:--\""}`

```ts
// src/hr/ShiftManagement.tsx:95-98  — a DISPLAY placeholder…

// …used to seed the EDIT form's field value:

p_half_day_cutoff_override: form.half_day_cutoff_override || null,          // :559
```

**Fix:** make `formatTimeValue` return `""` for the form path (keep "--:--" for display only), or

## BUG-09 · HR's Daily attendance view invents "Absent" for every unpunched employee

```
TITLE:      Daily attendance shows ABSENT for employees with no attendance row, contradicting
            both the documented design and the Summary tab on the same screen
CASE:       AT-09, AT-21
MODULE:     Attendance
SEVERITY:   Major
ACCOUNT:    hr-qa@talentmeshsolutions.com
WHEN:       2026-09-02 ~13:00 IST
BROWSER:    Brave, Windows 11

STEPS:
1. /hr/attendance → Daily tab, date 02-09-2026 (today, the default).
2. Then switch to the Summary tab for September 2026.

EXPECTED:   README §4.1 — an unpunched working day produces NO ROW, deliberately, because the
            system must not assert an absence it cannot know about. The screen should show a
            blank day, not "Absent".
ACTUAL:     Daily lists ALL SIX employees with a red ABSENT badge.
            Summary, on the same screen, reports DAYS ABSENT = 0 for all six.
```

**The database is right and the Daily view is wrong.** There are **zero** attendance rows for
2026-09-02 (also for 08-31 and 09-01), confirmed by direct query, and a derivation run *completed*
over 2026-08-31 → 2026-09-02 without producing any — exactly the documented behaviour.

**Root cause:** `src/hr/Attendance.tsx:478-489` builds a synthetic row for every employee with no
record on the selected date and hard-codes `status: "absent"`. The Summary tab (line 556) instead
counts real rows (`row.status === "absent"`), which is why the two disagree.

Why this matters beyond cosmetics: Daily is the **default landing tab** and defaults to **today**,
so every morning HR sees a full roster of false absences before anyone has punched — the precise
failure mode the no-row design was built to prevent. It is also the screen an HR user would act
on when correcting attendance.

**Fix:** render unpunched days as blank/"—" (or an explicit "No record yet"), not as Absent.
