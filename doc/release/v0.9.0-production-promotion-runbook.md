# Runbook: Track A, promoting v0.9.0 (non-payroll) to production

**Owner:** lead engineer · **Written:** 2026-09-23 · **Status:** gates 0–1 are waiting on the owner

This runbook promotes everything accepted on TB-M1M2 (P1–P3 and C1–C9) to the production parent. Payroll
stays **hidden**: it is removed from the frontend, and its data is not touched. Biometric work (Track B) is
**not** part of this release.

| Thing | Value |
|---|---|
| Production parent | `0431f0f6-225f-4fb1-86b7-3fd32684c7f4` (`rq3qmu8y`) |
| Test backend (do not promote *from* it; it is only where things were proven) | TB-M1M2 `fb9a8659-…` |
| Production frontend | Vercel, auto-deploys from GitHub `main` |
| Source branch | `p1-00-harness-reconciliation` |
| Migration head after this release | `20260912199000` |
| CLI | `node node_modules/@insforge/cli/dist/index.js` (written `$CLI` below). Do not use npx. |

**Rules for the whole runbook**
- Nothing is written to the parent until **Gate 0 and Gate 1 pass**, and the owner says "go" for **each** step
  marked 🔴.
- A push or merge to `main` **is** a production frontend deploy.
- The CLI is linked to TB by default. Every command aimed at production either passes
  `--project 0431f0f6-…` or runs after an explicit `link` to the parent. Check with `$CLI current` before
  every 🔴 step, and re-link to TB when you are done.
- There are no real users yet (all data is dummy), so a short maintenance window is acceptable. Still
  follow the order: the rehearsal is for the day real customers exist.

## Gate 1: rehearsal on a full branch of production

The rehearsal **replays the release steps A–E in order** on a full copy of production. Its purpose is
the in-between states: a frontend on an older schema, and old functions on a newer schema. Testing only
the end state would miss exactly those. It uses the parent's **last free branch slot**: the quota is 2
and TB-M1M2 holds one. Delete the branch when you finish so that Track B can have its own.

1. 🔴 Link the parent (read-only here) and do the key check, then branch:
   ```bash
   $CLI link --project-id 0431f0f6-225f-4fb1-86b7-3fd32684c7f4
   $CLI secrets get API_KEY | cut -c1-8                # current parent key prefix
   git grep -hoE "ik_[a-f0-9]{20,}" | cut -c1-8 | sort -u   # leaked prefixes; a match means rotate in step G
   $CLI db migrations list                               # PRODUCTION's real migration head -> record below
   $CLI branch create rehearsal-v090 --mode full         # auto-switches the link to the branch
   $CLI current                                          # must show rehearsal-v090
   ```
   Production migration head: `__________`. Every repo migration above it belongs to this release
   (`20260904120000` and `20260912180000`… are candidates; do not assume).
   **Branch quirk (found 2026-09-23):** a new branch lists its functions as `active`, but its functions host
   returns **404** until each one is redeployed. Redeploy production's own code (`functions code <slug>` →
   `functions deploy <slug> --file`), and pace it for the write rate limit.
2. **Harness change (its own small reviewed commit).** The suites import `TB_M1M2` by name, and
   `p3_private_buckets.mjs` asserts `linked.project_id === TB_M1M2.projectId`. Make the target
   selectable (e.g. `M1M2_TARGET=rehearsal`) in `tests/m1m2/_target.mjs`, keep TB as the default, and
   keep the parent refused. Then seed: `npm run test:m1m2:seed` and `npm run test:m1m2:personas`.
3. **Edge-function inventory (before any step).** For every slug in `functions/`, compare **three**
   copies: the repo, **TB** (the copy that passed the suites), and the branch (production's). A repo copy
   that differs from TB is **untested code**: stop and resolve it. The ones changed since `origin/main`:
   - modified: `create-employee-user`, `create-hr-admin-user`, `finalize-onboarding`,
     `set-employee-password`, `verify-employee-code`
   - new: `accept-tenant-invitation`, `manage-tenant-access`

     `auth-signup`, `auth-verify`, `daily-incomplete-task-marker`
   - **deleted from source:** `on-leave-reviewed`. Decide whether production still has it and whether
     anything calls it.

   For each changed function, note **which migration it needs** (for example, a function that calls
   an RPC created in `181000`) and **which old migration-revoked grant it relied on** (the rate limiter
   was revoked twice before). That decides where step D goes in the release plan.

## Release plan (production): each 🔴 needs the owner's "go"

**Corrected by the rehearsal of 2026-09-23** (details in `v0.9.0-rehearsal-report.md`). Production's head
was `20260904120000`, and **34 migrations** are pending (`20260912180000` → `20260912199000`), none out
of order.

Why this order:
- P3-02b needs the frontend **before** `191000`, and C3 needs `194000` **before** its frontend.
- Migration `187000` **refuses to run** while `hr-policies` is public. `189000` and `190000` require
  four more buckets to go private, and only the `b77afc8` frontend reads private files correctly.
- The changed functions call RPCs created in `181000`, and `b77afc8`'s Users & Access page calls
  them.
