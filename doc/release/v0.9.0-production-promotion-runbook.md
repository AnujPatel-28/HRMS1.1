# Runbook: Track A, promoting v0.9.0 (non-payroll) to production

**Owner:** lead engineer · **Written:** 2026-09-23 · **Status:** gates 0–1 are waiting on the owner

This runbook promotes everything accepted on TB-M1M2 (P1–P3 and C1–C9) to the production parent. Payroll
stays **hidden**: it is removed from the frontend, and its data is not touched. Biometric work (Track B) is
**not** part of this release.

| Production parent | `0431f0f6-225f-4fb1-86b7-3fd32684c7f4` (`rq3qmu8y`) |
| Test backend (do not promote *from* it; it is only where things were proven) | TB-M1M2 `fb9a8659-…` |

**Rules for the whole runbook**
- Nothing touches the parent until **Gate 0 and Gate 1 pass**, and the owner says "go" for **each** step
  marked 🔴.
- A push or merge to `main` **is** a production frontend deploy.
- The CLI is linked to TB by default. Every command aimed at production either passes
  `--project 0431f0f6-…` or runs after an explicit `link` to the parent. Check with `$CLI current` before
  every 🔴 step, and re-link to TB when you are done.
- There are no real users yet (all data is dummy), so a short maintenance window is acceptable. Still
  follow the order: the rehearsal is for the day real customers exist.

## Gate 1: rehearsal on a full branch of production

This uses the parent's **last free branch slot**. The quota is 2 and TB-M1M2 holds one. Delete the
rehearsal branch when you finish so that Track B can have its own.

1. 🔴 `$CLI link --project-id 0431f0f6-225f-4fb1-86b7-3fd32684c7f4` → `$CLI branch create rehearsal-v090 --mode full`
   (this auto-switches the link to the new branch) → `$CLI current` shows `rehearsal-v090`.
2. `$CLI db migrations list` **on the rehearsal branch** tells you which migrations production really
   has. Record the head here: `__________`. Every repo migration above that head is part of this release.
   `20260904120000` and `20260912180000`… are candidates. Do not assume.
3. **Edge functions:** diff **every** function in `functions/` against the branch with
   `$CLI functions code <slug>` before you deploy anything. The ones changed since `origin/main` are:
   - modified: `create-employee-user`, `create-hr-admin-user`, `finalize-onboarding`,
     `set-employee-password`, `verify-employee-code`
   - new: `accept-tenant-invitation`, `manage-tenant-access`
   - source added for functions production already runs: `admin-auth-login`, `auth-session`,
     `auth-signup`, `auth-verify`, `daily-incomplete-task-marker`
   - **deleted from source:** `on-leave-reviewed`. Check whether production still has it and whether
     anything calls it.

   Never deploy a function blind; six production functions had no source in the repo.
4. Apply migrations in the order of the release plan below, **against the branch**.
5. **Harness:** the suites are hard-wired to TB (`tests/m1m2/_target.mjs`). Add a `REHEARSAL` target
   there, following the TB pattern with the branch's id and hosts. Then run `npm run test:m1m2:seed` and

   ```bash
   for f in tests/m1m2/[cp][0-9]*.mjs; do node "$f" > "logs/$(basename $f).log" 2>&1; rc=$?; echo "$(basename $f) rc=$rc"; done
   grep -lE "AssertionError|HarnessBlocked|^FAIL" logs/*.log
   ```

   Pass bar: every suite exits 0, except the accepted `p3_realtime_isolation` item 6.
6. Point a local frontend at the branch (`VITE_INSFORGE_URL` / anon key / functions URL). Smoke-test as HR
   and as an employee: sign in, punch in/out, request leave, approve it, and confirm no payroll menu

7. Write the result to `doc/release/v0.9.0-rehearsal-report.md`, including production's real migration

**Rollback:** the frontend goes back through a Vercel "promote previous deployment". The database is
restored with `backups restore <id> --project 0431f0f6-…`, which **overwrites all data**, so it needs the
owner's go. Migrations are forward-only, so a small defect gets a forward fix, not a restore.
