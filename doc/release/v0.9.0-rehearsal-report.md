## Finding (not a release blocker): leave approval checks status before permission

`approve_leave_request` (live body from `20260912196000`) locks the leave `FOR UPDATE` and raises
`Leave request is no longer pending (current status: …)` **before** calling `assert_leave_reviewer`. A
signed-in user from **any** tenant who has a leave's UUID learns its status, and briefly holds a row lock
on it, instead of getting a denial. Nothing is approved and nothing changes. The UUIDs are random and
all data is dummy, so the risk is **low**. This already exists on TB; the release did not introduce it.
`cancel_leave_request` authorizes first and is fine.

- **How it surfaced:** `p1_membership_invitation_revocation` uses a hard-coded QA-tenant leave
  (`83f1421d…`). It was pending in TB's 13-Sep snapshot, and production has since approved it.
- **Rehearsal handling:** that leave was set back to `pending` on the rehearsal branch only
  (`scratch/rehearsal-reset-pending-leave.mjs`), then the suite passed in full.
- **Follow-up (after v0.9.0, as package C10):**
  - call `assert_leave_reviewer` before the status check, and look for the same ordering in other
    `*_request` RPCs
  - give the suite its own pending leave in Company B instead of real QA-tenant data
