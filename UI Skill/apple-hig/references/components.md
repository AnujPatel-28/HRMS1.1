# Components — Apple HIG Reference

Source: developer.apple.com/design/human-interface-guidelines/components

---

## Buttons

### Button Roles
| Role | Use | Visual |
|---|---|---|
| Primary | Main CTA, one per screen | Filled, tinted (system blue) |
| Secondary | Supporting action | Outlined or tinted subtle |
| Destructive | Deletes / removes data | Red (`systemRed`) |
| Plain | Inline or in toolbars | No fill, tinted label |
| Borderless | In lists, navigation | Text only |

**Rules:**
- Maximum **one primary action per screen**. Multiple filled buttons competing for attention is an anti-pattern
- Button labels: use verbs that describe what happens ("Save", "Delete", "Add to Cart") — never vague ("OK", "Confirm" without context)
- Minimum touch target: **44×44pt** even if the visual is smaller (add invisible padding)
- Disable buttons rather than hiding them when the action is temporarily unavailable — users need to know what's possible
- Destructive actions require confirmation (an alert) before executing — never trigger immediately on first tap

### Button Styles (iOS 26 / SwiftUI)
```swift
Button("Save") { }                          // .automatic
Button("Save") { }.buttonStyle(.borderedProminent) // Primary (filled)
Button("Cancel") { }.buttonStyle(.bordered)         // Secondary
Button("Delete", role: .destructive) { }   // Destructive
```

### System Buttons
- **Back:** Auto-generated by NavigationStack — never recreate it
- **Close/Done:** Use "Done" in modal nav bars. Use "✕" only for icon-only dismissal (and add accessibilityLabel)
- **Edit:** Standard pattern — Edit mode shows delete controls and reorder handles

## Lists

Lists are the backbone of iOS content display. Use `List` in SwiftUI / `UITableView` in UIKit.

**Anatomy of a list row:**
- Leading: icon or thumbnail (optional)
- Body: primary label + optional subtitle
- Trailing: disclosure indicator (›), value text, badge, switch, or chevron
- Optional: swipe actions (leading for positive, trailing for destructive)

**Row height:** System default is ~44pt minimum. Content-driven rows grow as needed.

**Section headers:** Short, uppercase, `.footnote` weight. Describe the group, not repeat the list title.

**Swipe actions:**
- Trailing swipe: destructive actions (Delete). Delete is always destructive red
- Leading swipe: contextual positive actions (Archive, Pin, Mark as Read)
- Keep swipe actions to 2–3 maximum per row
- The full-swipe gesture on trailing edge should trigger the primary trailing action (usually Delete with confirmation)

**Separators:**
- System-managed — don't remove them without reason. They signal list structure
- Remove separators in card-based or icon-grid layouts

**Selection:**
- Single selection: row highlight + checkmark on selected
- Multi-selection: use Edit mode (checkmarks appear) rather than tap-to-toggle in browse mode
- Empty selection = empty state, not an error

**Empty list:** Always show an empty state (see `references/states.md`)

## Cards

Cards are grouping containers — content blocks with rounded corners that sit above the background.

**HIG rules for cards:**
- Use `.systemBackground` (white/dark adaptive) for card surface
- Corner radius: `12–16pt` for standard cards; `10pt` for compact
- Shadow: subtle — `y:2, blur:8, opacity:0.08` in light mode. Cards in dark mode typically don't use shadows (they blend)
- Padding inside card: `16pt` horizontal, `12–16pt` vertical
- Cards should not have visible borders in iOS 26 — elevation (shadow or Liquid Glass) creates separation

**Card tap behavior:**
- The entire card is the tap target — not just the title or a "View" button inside
- Show a pressed state (`.scaleEffect(0.97)` or dimming) on touch-down

**When to use cards vs. lists:**
- Cards: heterogeneous content blocks, featured/editorial content, dashboards
- Lists: homogeneous rows of the same type, settings, options

## Sheets (Bottom Sheets)

A sheet slides up from the bottom. It covers part of the screen (resizable) or the full screen.

**Detents (iOS 16+):**
- `.medium` — sheet covers ~half the screen; content above the sheet is still visible and interactive
- `.large` — sheet covers nearly full screen; background is dimmed, content above is not interactive
- Custom detents: specify exact height or fraction in SwiftUI

**Sheet rules:**
- Support swipe-to-dismiss unless data would be lost (then intercept and confirm)
- Always include a drag handle (grabber) at the top when the sheet is resizable
- Include a navigation bar inside the sheet if it has its own flow
- Sheets can contain navigation stacks, but keep it shallow (1–2 levels) before pushing to a full-screen modal
- Do not present a sheet from inside another `.medium` sheet — use `.large` instead

**When sheet vs. navigation push:**
- Sheet: transient task, loosely coupled to current context
- Push: part of the same hierarchy, user will return via Back

## Forms (Input)

### Text Fields
- Label sits above the field (not as a placeholder) for complex forms
- Placeholder text = example value or hint, not the label
- Use `.textContentType()` to enable system autofill (email, password, address)
- Use `.keyboardType()` to show appropriate keyboard (number pad for phone, email keyboard for email)
- Always show validation feedback inline — not just on submit

### Pickers / Selectors
| Component | Use |
|---|---|
| `Toggle` | Binary on/off state |
| `Stepper` | Incrementing/decrementing a specific value |
| `Slider` | Continuous range (volume, brightness) |
| `Picker` (wheel) | Short finite list (day/month/year) |
| `DatePicker` | Date and/or time selection |
| `Menu` / Action Sheet | Choosing from multiple options |

**Prefer system controls.** They come with built-in accessibility, haptics, Dynamic Type support, and Dark Mode. Custom pickers require you to rebuild all of that.

### Form Sections
- Group related fields into labeled sections with `Section` headers
- Order: most-used fields first, destructive actions at the bottom
- "Save" / "Done" goes in the navigation bar (top-right), not as a full-width button at the bottom of a form (unless it's a simple one-screen form with no nav bar)

### Keyboards
- Dismiss keyboard when user taps outside the field or taps "Done"
- Never obscure your form with the keyboard — use `ScrollView` and keyboard avoidance
- Use the Return key label that matches the action: "Done", "Next", "Search", "Go"

## Alerts and Action Sheets

### Alerts
- Use for **critical information** that requires an immediate decision
- Maximum 2 actions (preferred). 3 actions allowed, but rare
- **Title:** Describes the situation
- **Body:** Optional. Explains consequence. Keep to one sentence
- **Buttons:** Right button = default/primary. Left button = cancel
- **Destructive button** = red, placed on the left (not the right)
- Never use an alert for simple confirmation of success — use a Toast/Banner instead

```swift
Alert(
    title: Text("Delete Item?"),
    message: Text("This action cannot be undone."),
    primaryButton: .destructive(Text("Delete")) { deleteItem() },
    secondaryButton: .cancel()
)
```

### Action Sheets (iOS: `.confirmationDialog`)
- Use when user needs to choose between 3+ actions
- Bottom sheet with full-width buttons
- Cancel is always present and always at the bottom
- Destructive action is red and near the top (never adjacent to Cancel)
- **Do not use action sheets for navigation** — use menus instead

## Search

**Primary search entry point (iOS 26):** Circular Liquid Glass island at the right end of the tab bar — tap to expand search inline.

**Secondary:** Search field in navigation bar at top of a list view (`.searchable` modifier).

**Behavior:**
- Search activates: keyboard appears, optional scopes/filters appear below search bar
- Optionally show recent searches and/or popular/suggested searches before the user types
- Results update as user types (live search) — no manual "Search" button needed
- Empty result state: clear message + suggestion to try different terms
- Cancel button dismisses search and restores the previous view

**Scopes:**
- Use segmented control below search bar for filtering across categories
- Max 4 scopes; labels short enough to fit without truncation

**SwiftUI:**
```swift
.searchable(text: $query, placement: .navigationBarDrawer(displayMode: .always))
.searchScopes($scope) {
    ForEach(Scope.allCases) { scope in
        Text(scope.label).tag(scope)
    }
}
```
